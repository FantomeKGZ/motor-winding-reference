# Проверка изображений каталога схем

Статус: активно для внешнего сайта `motor-winding-reference`.

## Зачем это нужно

В старом справочнике перед некоторыми настоящими рисунками укладки находятся маленькие служебные изображения, например `images/sovmob/met3.jpg` с пометкой рекомендуемого укорочения шага.

Такой значок является частью исходной страницы и не должен удаляться из старого HTML. Но он также не должен попадать в `scheme-catalog.json` как основное изображение схемы.

Аналогичное правило действует для `CM-CON-*`: если каталог утверждает, что конкретный вариант подключения имеет собственное изображение, это изображение должно реально существовать и реально присутствовать на соответствующей `ss*.html` странице.

Исходный справочник в `sourse/` остаётся неизменяемым.

## Автоматическая цепочка

GitHub Actions выполняет каталог в следующем порядке:

```text
build_scheme_catalog.py
        ↓
repair_scheme_catalog_images.py
        ↓
validate_scheme_catalog_images.py
        ↓
validate_connection_option_images.py
        ↓
validate_scheme_catalog.py
        ↓
artifact JSON
```

Обработка выполняется отдельно для desktop и mobile.

## Repair изображений укладки

Инструмент:

```text
tools/repair_scheme_catalog_images.py
```

Он читает уже построенный производный JSON-каталог и проверяет поле `image` каждой схемы.

Если `image` выглядит как служебный marker/icon, инструмент повторно открывает только соответствующую `legacy_page`, находит абзац описания `Схема укладки ...` и выбирает первое настоящее изображение схемы из этого или ближайшего следующего абзаца.

При замене изображения обязательно пересчитывается `scheme_id`, потому что стабильный идентификатор определяется парой:

```text
legacy_page + image
```

Формат остаётся:

```text
CM-SCH-XXXXXXXXXXXX
```

Отчёты ремонта:

```text
site/shared/data/desktop-scheme-catalog-image-repair.json
site/shared/data/mobile-scheme-catalog-image-repair.json
```

Они показывают старое изображение, новое изображение, старый `scheme_id` и новый `scheme_id`.

## Проверка изображений укладки

Инструмент:

```text
tools/validate_scheme_catalog_images.py
```

После repair он заново проверяет весь каталог. В частности, каталог не должен содержать в качестве изображения укладки служебные пути вроде:

```text
images/sovmob/met3.jpg
images/sovmob/met*.gif
```

Если подозрительное изображение осталось, CI завершается с ошибкой и такой каталог не считается готовым к использованию.

## Проверка изображений схем подключения

Инструмент:

```text
tools/validate_connection_option_images.py
```

Он проверяет уже сформированные `connection_options[]` и особенно варианты со `scope: "image"`.

Для каждого такого `CM-CON-*` должны одновременно выполняться условия:

- присутствует `image`;
- путь не выглядит как marker/icon;
- соответствующая `ss*.html` страница существует;
- файл изображения существует в исходном справочнике;
- именно эта `ss*.html` страница действительно содержит ссылку на это изображение;
- `connection_id` соответствует детерминированному правилу `page + image + type`.

Для `scope: "page"` действует обратное правило: конкретная картинка не заявляется. Это означает, что старый HTML позволил подтвердить страницу/тип подключения, но не позволил безопасно связать его с отдельным рисунком.

Такой page-level вариант лучше, чем ошибочно показать пользователю чужую картинку звезды или треугольника.

Отчёты CI:

```text
site/shared/data/desktop-connection-option-image-validation.json
site/shared/data/mobile-connection-option-image-validation.json
```

## Почему нельзя просто брать первую картинку со страницы `ss*.html`

Одна старая страница подключения может содержать:

- общую иллюстрацию;
- звезду;
- треугольник;
- несколько вариантов для разных `a`;
- служебные изображения;
- технический текст между изображениями.

Поэтому правило `первая картинка = нужная схема` запрещено. Каталог должен либо иметь подтверждённую связь конкретного `CM-CON-*` с конкретным изображением, либо сохранить вариант как `scope: "page"` без придуманного preview.

## Общая проверка каталога

Только после обеих проверок изображений запускается:

```text
tools/validate_scheme_catalog.py
```

Он проверяет идентификаторы схем и подключений, количество `connections`, `connection_options`, битые страницы и совпадение desktop/mobile.

Это важно: общий валидатор получает уже проверенную структуру, которая будет использоваться Scheme Picker и карточкой двигателя.

## Почему repair остаётся отдельным этапом

Сейчас старый справочник содержит много исторических HTML-вариантов. Отдельный repair-этап даёт безопасный переходный слой:

- исходный HTML не меняется;
- генератор каталога остаётся читающим исходные данные;
- исправления можно увидеть отдельным отчётом;
- появление нового типа служебной картинки будет видно в CI;
- стабильные `CM-SCH-*` формируются по фактически используемому изображению.

В дальнейшем логику выбора настоящего изображения можно перенести непосредственно в `build_scheme_catalog.py`. Даже после этого обе image-validation проверки желательно оставить как защиту от регрессий.

## Требование для будущего ИИ

При дальнейшем развитии каталога ChatGPT/ИИ не должен удалять marker-изображения из старых страниц только потому, что они не являются схемами. Они могут иметь смысл для мастера.

Нужно различать:

```text
legacy page content              — сохраняется полностью;
derived scheme.image             — настоящий рисунок укладки;
derived connection_option.image  — только подтверждённый рисунок конкретного подключения.
```

Если соответствие конкретной схемы подключения и изображения неоднозначно, ИИ должен сохранить page-level вариант без изображения, а не угадывать.

Работа в этом репозитории по-прежнему относится только к внешнему сайту. Реализация ESP32 выполняется позже по `ESP32_CONNECTION_HANDOFF.md` после отдельного указания пользователя.
