# Аудит неоднозначных схем подключения

Статус: внешний сайт `motor-winding-reference`; ESP32 не изменяется.

## Зачем нужен аудит

Каталог CoilMaster различает два уровня достоверности для схем подключения:

- `scope: "image"` — конкретная картинка надёжно связана с конкретным `CM-CON-*`;
- `scope: "page"` — известна реальная `ss*.html` страница, но конкретную картинку безопасно определить пока нельзя.

`scope: "page"` остаётся допустимым и безопасным состоянием. Оно лучше, чем ошибочно показать мастеру неверную звезду, треугольник или специальную схему.

## Текущее контрольное состояние

После последовательного улучшения общих правил распознавания контрольная сборка каталога дала:

```text
unique_page_scoped_connection_options: 0
unique_pages_with_page_scoped_options: 0
page_scoped_options_with_unknown_type: 0
page_scoped_options_with_known_type: 0
```

То есть на текущем архиве старого справочника все найденные выбираемые варианты подключения удалось связать с конкретными проверенными изображениями без ручных исключений по именам отдельных страниц.

Это не означает, что механизм `scope: "page"` нужно удалить. Он остаётся обязательным резервным состоянием для будущих страниц и изменений исходного справочника.

## Как удалось убрать текущие неоднозначности

Применены общие правила, подтверждённые реальными HTML-шаблонами:

- отдельное распознавание `star`, `delta` и комбинированного `star_delta`;
- однофазные страницы разделяются на соединение самой обмотки и подключение двигателя к сети;
- двухскоростные страницы разделяются на соединение обмотки и подключение к сети;
- трёхскоростные страницы обрабатываются аналогично, включая случаи, где после одной подписи идут несколько последовательных картинок;
- распознаются страницы совмещённых обмоток;
- сохраняются явно записанные `a` и `соединение фаз`;
- старые страницы с mojibake декодируются по содержимому, без изменения файлов в `sourse/`;
- служебные marker/icon изображения никогда не становятся превью подключения.

Контрольная сборка после этих изменений содержит 828 уникальных `CM-CON-*`. Во всех 5753 использованиях connection-options внутри схем каталог указывает `scope: "image"`; валидатор конкретных картинок проходит с нулём ошибок.

## Инструмент

```text
tools/audit_page_scoped_connections.py
```

Он не изменяет каталог и старые HTML-файлы. Если в будущем снова появятся неоднозначные страницы, инструмент автоматически сформирует рабочую очередь для дальнейшего улучшения распознавания.

Для каждой неоднозначной страницы считаются:

- `reference_count` — сколько раз варианты этой страницы используются схемами укладки;
- `scheme_count` — сколько различных `CM-SCH-*` зависят от страницы;
- `option_count` — сколько уникальных page-scoped `CM-CON-*` относится к странице;
- распознанные `types`;
- количество вариантов с неизвестным типом.

Страницы сортируются по приоритету: сначала те, исправление которых улучшит наибольшее количество карточек и вариантов укладки.

## Отчёты CI

```text
site/shared/data/desktop-page-scoped-connection-audit.json
site/shared/data/mobile-page-scoped-connection-audit.json
```

При текущем архиве массив `priority_pages` пуст. Если новая неоднозначность появится, она снова автоматически попадёт в этот отчёт.

## Правило дальнейшей работы

При улучшении распознавания нельзя автоматически превращать `scope: "page"` в `scope: "image"` только потому, что на странице есть одна или несколько картинок.

Для перехода к `scope: "image"` требуется подтверждённая связь:

```text
подпись/контекст типа подключения
        ↓
конкретная картинка или группа картинок до следующего смыслового заголовка
        ↓
реальная ссылка внутри той же ss*.html
        ↓
детерминированный CM-CON-*
```

Если связь неоднозначна, вариант должен снова остаться `scope: "page"`, даже если это ухудшит внешний вид карточки.

## Дополнительный аудит шаблонов

`tools/audit_connection_page_templates.py` остаётся в CI даже при нулевом числе текущих page-scoped вариантов. Он нужен как диагностический инструмент, если после добавления новых страниц или изменения правил появится новая неоднозначность.

Главный принцип для будущего виджета карточки двигателя остаётся прежним:

> отсутствие маленького превью допустимо, неверное превью — нет.
