# Каталог схем CoilMaster

## Назначение

`tools/build_scheme_catalog.py` строит производный каталог схем из неизменяемых HTML-файлов старого справочника. Исходники в `sourse/` не редактируются.

Каталог создаётся отдельно для desktop и mobile:

- `site/shared/data/desktop-scheme-catalog.json`;
- `site/shared/data/mobile-scheme-catalog.json`.

Эти JSON-файлы генерируются GitHub Actions и попадают в артефакт проверки. После валидации структуры они могут использоваться внешним сайтом вместо повторного разбора HTML при каждом поиске.

## Что считается отдельной схемой укладки

Отдельной записью считается конкретный рисунок укладки внутри старой HTML-страницы.

Ключ записи строится из:

`legacy_page + image`

и преобразуется в детерминированный идентификатор вида:

`CM-SCH-XXXXXXXXXXXX`

Это не последовательный номер. Добавление новых схем не должно перенумеровывать существующие записи.

## Основные поля схемы

Для каждой схемы каталог пытается сохранить только явно присутствующие в исходнике данные:

- `scheme_id` — стабильный идентификатор CoilMaster;
- `legacy_page` — старая HTML-страница;
- `image` — конкретный рисунок укладки;
- `description` — исходное текстовое описание варианта;
- `slots` — число пазов;
- `rpm` — обороты;
- `poles` — `2p`;
- `q` — число пазов на полюс и фазу;
- `winding_types` — распознанные типы обмотки;
- `pitch` — явно записанный шаг `y`;
- `parallel_branches` — допустимые значения `a`;
- `special` — явные признаки специальных/многоскоростных схем;
- `connections` — все найденные уникальные страницы схем подключения;
- `connection_count` — количество уникальных связанных страниц подключения;
- `connection_options` — конкретные выбираемые варианты подключения;
- `connection_option_count` — количество таких вариантов.

Неизвестные параметры не вычисляются по имени файла и не подставляются по догадке.

## Несколько страниц подключения

Одна схема укладки может иметь одну или несколько связанных схем подключения. Поэтому `connections` всегда является массивом.

Важно: в старом HTML одна и та же `ss*.html` ссылка иногда повторяется несколько раз внутри одного описания. Начиная с версии каталога 2 такие повторные `<a>` не увеличивают `connection_count`: одна физическая страница подключения учитывается один раз. Если рядом действительно указаны две разные страницы `ss*.html`, обе сохраняются.

## Версия 3: стабильные идентификаторы подключений

Для интеграции с карточкой двигателя одного `scheme_id` недостаточно. Если у выбранной укладки несколько допустимых подключений, нужно уметь сохранить именно тот вариант, который мастер фактически использовал.

Поэтому каталог версии 3 вводит стабильные идентификаторы подключения:

`CM-CON-XXXXXXXXXXXX`

Идентичность конкретного подключения строится детерминированно из:

`connection page + concrete image + normalized type`

Если старый HTML позволяет определить тип (`star`, `delta`, специальная схема), но не позволяет надёжно связать его с конкретной картинкой, создаётся page-level вариант:

`connection page + type`

Если даже тип нельзя определить надёжно, реальная ссылка на `ss*.html` всё равно не теряется: создаётся один `unknown` page-level вариант.

Таким образом, каталог никогда не выдумывает картинку подключения, но и не выбрасывает существующую связь.

### Структура страницы подключения

Каждый элемент `connections[]` теперь содержит:

- `page` — исходная `ss*.html`;
- `page_id` — стабильный `CM-CON-PAGE-*` технический идентификатор страницы;
- `types` — найденные типы;
- `images` — конкретные распознанные изображения;
- `options` — выбираемые варианты с `connection_id`;
- `special` — специальные признаки.

### Плоский список для интерфейса

На уровне каждой схемы укладки формируется `connection_options[]`. Это объединённый, дедуплицированный список всех выбираемых подключений всех связанных `ss*.html`.

Пример:

```json
{
  "scheme_id": "CM-SCH-...",
  "connection_count": 2,
  "connection_option_count": 4,
  "connection_options": [
    {
      "connection_id": "CM-CON-...",
      "page": "ss2k3000a2.html",
      "type": "star",
      "image": "images/ss3000/2k3000a2_zv.jpg",
      "scope": "image"
    },
    {
      "connection_id": "CM-CON-...",
      "page": "ss2k3000a2.html",
      "type": "delta",
      "image": "images/ss3000/2k3000a2_tr.jpg",
      "scope": "image"
    }
  ]
}
```

Этот список предназначен прежде всего для будущего Scheme Picker и виджета карточки двигателя.

## Связь с карточкой двигателя ESP32

Рекомендуемая модель:

`motor record -> scheme_id -> catalog`

и при необходимости:

`motor record -> connection_id -> one option inside selected scheme`

ESP32 не должна копировать в каждую карточку двигателя весь `connections[]`, HTML или большие изображения. В записи двигателя достаточно хранить стабильные ссылки.

Подробная спецификация стороны CoilMaster находится в:

`FantomeKGZ/CoilMaster/Docs/AI_CONTEXT/MOTOR_SCHEME_BINDING_SPEC.md`

## Проверенная статистика каталога версии 2

Контрольная сборка версии 2 завершилась успешно. Desktop и mobile дали одинаковую структуру и одинаковый набор `scheme_id`.

Для каждой версии справочника:

- `pages_scanned`: 928;
- `pages_with_variants`: 370;
- `schemes`: 1074;
- `connection_pages`: 311;
- `schemes_without_connection_pages`: 183;
- `schemes_with_one_connection_page`: 344;
- `schemes_with_multiple_connection_pages`: 547;
- `max_connection_pages_per_scheme`: 8.

Распределение по числу уникальных страниц подключения:

- 0 страниц: 183 схемы;
- 1 страница: 344 схемы;
- 2 страницы: 274 схемы;
- 3 страницы: 113 схем;
- 4 страницы: 121 схема;
- 5 страниц: 8 схем;
- 6 страниц: 25 схем;
- 8 страниц: 6 схем.

Это подтверждает требование интерфейса: количество подключений надо показывать для конкретной укладки, а не только для группы пазов/оборотов.

## Новая статистика версии 3

После генерации версия 3 дополнительно считает:

- `connection_options` — число уникальных `CM-CON-*` во всём каталоге;
- `schemes_without_connection_options`;
- `schemes_with_one_connection_option`;
- `schemes_with_multiple_connection_options`;
- `max_connection_options_per_scheme`.

Эти показатели лучше отражают будущий пользовательский интерфейс, потому что одна `ss*.html` страница сама может содержать несколько реально выбираемых подключений, например звезду и треугольник.

## Автоматическая проверка целостности

`tools/validate_scheme_catalog.py` теперь проверяет:

- уникальность всех `scheme_id`;
- уникальность пары `legacy_page + image`;
- отсутствие повторяющихся страниц внутри `connections` одной схемы;
- соответствие `connection_count` реальному размеру массива;
- наличие `page_id` у страниц подключения;
- наличие `connection_id` у каждого выбираемого варианта;
- отсутствие дублирующихся `connection_id` внутри одной схемы;
- что один и тот же `connection_id` всегда означает одну и ту же комбинацию `page/image/type/scope`;
- что `connection_option_count` соответствует массиву;
- отсутствие ссылок на отсутствующие страницы подключения;
- соответствие статистики реальному распределению;
- одинаковый набор `scheme_id` у desktop и mobile;
- одинаковый набор и семантику `connection_id` у desktop и mobile.

Результат сохраняется в `site/shared/data/scheme-catalog-validation.json`. Ошибка любой проверки завершает CI с ошибкой.

## Следующее использование

После проверки версии 3 внешний сайт сможет работать по схеме:

`ESP32 motor -> scheme_id -> схема укладки -> connection_options[] -> выбранный connection_id`.

Это является основой для компактного виджета схем в карточке двигателя и единого Scheme Picker при добавлении/редактировании двигателя.

До завершения проверки старый HTML-разбор остаётся резервным и контрольным механизмом.
