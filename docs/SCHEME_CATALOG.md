# Каталог схем CoilMaster

## Назначение

`tools/build_scheme_catalog.py` строит производный каталог схем из неизменяемых HTML-файлов старого справочника. Исходники в `sourse/` не редактируются.

Каталог создаётся отдельно для desktop и mobile:

- `site/shared/data/desktop-scheme-catalog.json`;
- `site/shared/data/mobile-scheme-catalog.json`.

На текущем этапе эти JSON-файлы генерируются GitHub Actions и попадают в артефакт проверки. После валидации структуры их можно будет использовать непосредственно внешним сайтом вместо повторного разбора HTML при каждом поиске.

## Что считается отдельной схемой

Отдельной записью считается конкретный рисунок укладки внутри старой HTML-страницы.

Ключ записи строится из:

`legacy_page + image`

и преобразуется в детерминированный идентификатор вида:

`CM-SCH-XXXXXXXXXXXX`

Это не последовательный номер. Такой формат выбран специально, чтобы добавление новых схем не перенумеровывало уже существующие записи.

## Основные поля

Для каждой схемы каталог пытается сохранить только явно присутствующие в исходнике данные:

- `scheme_id` — стабильный идентификатор CoilMaster;
- `legacy_page` — старая HTML-страница;
- `image` — конкретный рисунок укладки;
- `description` — исходное текстовое описание варианта;
- `slots` — число пазов;
- `rpm` — обороты;
- `poles` — `2p`;
- `q` — число пазов на полюс и фазу;
- `winding_types` — распознанные типы обмотки;
- `pitch` — явно записанный шаг `y`;
- `parallel_branches` — допустимые значения `a`;
- `special` — явные признаки специальных/многоскоростных схем;
- `connections` — все найденные уникальные страницы схем подключения;
- `connection_count` — количество уникальных связанных страниц подключения.

Неизвестные параметры не вычисляются по имени файла и не подставляются по догадке.

## Несколько схем подключения

Одна схема укладки может иметь одну или несколько связанных схем подключения. Поэтому `connections` всегда является массивом.

Пример структуры:

```json
{
  "connection_count": 2,
  "connections": [
    {
      "page": "ss2k3000a1.html",
      "types": ["star", "delta"],
      "images": []
    },
    {
      "page": "ss2k3000a2.html",
      "types": ["star", "delta"],
      "images": []
    }
  ]
}
```

Каталог не выбирает одну из них автоматически. Все варианты должны быть доступны интерфейсу и пользователю.

Важно: в старом HTML одна и та же `ss*.html` ссылка иногда повторяется несколько раз внутри одного описания. Начиная с версии каталога 2 такие повторные `<a>` не увеличивают `connection_count`: одна физическая страница подключения учитывается один раз. Если рядом действительно указаны две разные страницы `ss*.html`, обе сохраняются.

## Схемы соединений

Для каждой связанной страницы `ss*.html` генератор дополнительно пытается определить:

- поддерживается ли соединение `star`;
- поддерживается ли `delta`;
- специальные признаки, например двухскоростная/трёхскоростная схема, двойная звезда или переключение полюсов;
- конкретные изображения соединений, если связь между подписью и рисунком определяется однозначно.

Страница соединения и рисунок укладки остаются отдельными сущностями. Они не получают один общий идентификатор.

## Проверенная статистика каталога версии 2

Контрольная сборка GitHub Actions завершилась успешно. Desktop и mobile дали полностью одинаковую структуру и одинаковый набор `scheme_id`.

Для каждой версии справочника получены следующие числа:

- `pages_scanned`: 928;
- `pages_with_variants`: 370;
- `schemes`: 1074;
- `connection_pages`: 311;
- `schemes_without_connection_pages`: 183;
- `schemes_with_one_connection_page`: 344;
- `schemes_with_multiple_connection_pages`: 547;
- `max_connection_pages_per_scheme`: 8.

Распределение по числу уникальных страниц подключения:

- 0 страниц: 183 схемы;
- 1 страница: 344 схемы;
- 2 страницы: 274 схемы;
- 3 страницы: 113 схем;
- 4 страницы: 121 схема;
- 5 страниц: 8 схем;
- 6 страниц: 25 схем;
- 8 страниц: 6 схем.

Таким образом, требование показывать пользователю все варианты подключения подтверждено фактическими данными: более половины распознанных схем укладки имеют несколько уникальных страниц подключения.

Для примера, в обычной группе `36 пазов / 3000 об/мин` встречаются варианты с двумя отдельными страницами подключения `ss2k3000a1.html` и `ss2k3000a2.html`, а некоторые варианты используют одну общую страницу `ss12k3000.html`. То есть количество подключений действительно зависит от конкретной схемы укладки, а не только от группы пазов и оборотов.

## Автоматическая проверка целостности

Добавлен `tools/validate_scheme_catalog.py`. После генерации GitHub Actions проверяет:

- уникальность всех `scheme_id`;
- уникальность пары `legacy_page + image`;
- отсутствие повторяющихся страниц внутри `connections` одной схемы;
- соответствие `connection_count` реальному размеру массива;
- отсутствие ссылок на отсутствующие страницы подключения;
- соответствие статистики реальному распределению `0 / 1 / несколько`;
- одинаковый набор `scheme_id` у desktop и mobile.

Результат сохраняется в `site/shared/data/scheme-catalog-validation.json`. Ошибка любой из этих проверок завершает CI с ошибкой, чтобы потеря или дублирование схем не прошли незаметно.

## Использование в будущем

После проверки качества каталога внешний сайт сможет работать по схеме:

`ESP32 context -> scheme catalog -> список кандидатов -> конкретная укладка + все варианты подключения`.

Это позволит сократить количество динамических чтений старых HTML-файлов и даст стабильную основу для сохранения `scheme_id` в проектах ESP32.

До завершения проверки старый HTML-разбор остаётся резервным и контрольным механизмом.
