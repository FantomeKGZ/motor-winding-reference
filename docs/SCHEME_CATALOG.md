# Каталог схем CoilMaster

## Назначение

`tools/build_scheme_catalog.py` строит производный каталог схем из неизменяемых HTML-файлов старого справочника. Исходники в `sourse/` не редактируются.

Каталог создаётся отдельно для desktop и mobile:

- `site/shared/data/desktop-scheme-catalog.json`;
- `site/shared/data/mobile-scheme-catalog.json`.

На текущем этапе эти JSON-файлы генерируются GitHub Actions и попадают в артефакт проверки. После валидации структуры их можно будет использовать непосредственно внешним сайтом вместо повторного разбора HTML при каждом поиске.

## Что считается отдельной схемой

Отдельной записью считается конкретный рисунок укладки внутри старой HTML-страницы.

Ключ записи строится из:

`legacy_page + image`

и преобразуется в детерминированный идентификатор вида:

`CM-SCH-XXXXXXXXXXXX`

Это не последовательный номер. Такой формат выбран специально, чтобы добавление новых схем не перенумеровывало уже существующие записи.

## Основные поля

Для каждой схемы каталог пытается сохранить только явно присутствующие в исходнике данные:

- `scheme_id` — стабильный идентификатор CoilMaster;
- `legacy_page` — старая HTML-страница;
- `image` — конкретный рисунок укладки;
- `description` — исходное текстовое описание варианта;
- `slots` — число пазов;
- `rpm` — обороты;
- `poles` — `2p`;
- `q` — число пазов на полюс и фазу;
- `winding_types` — распознанные типы обмотки;
- `pitch` — явно записанный шаг `y`;
- `parallel_branches` — допустимые значения `a`;
- `special` — явные признаки специальных/многоскоростных схем;
- `connections` — все найденные страницы схем подключения;
- `connection_count` — количество связанных страниц подключения.

Неизвестные параметры не вычисляются по имени файла и не подставляются по догадке.

## Несколько схем подключения

Одна схема укладки может иметь одну или несколько связанных схем подключения. Поэтому `connections` всегда является массивом.

Пример структуры:

```json
{
  "connection_count": 2,
  "connections": [
    {
      "page": "ss2k3000a1.html",
      "types": ["star", "delta"],
      "images": []
    },
    {
      "page": "ss2k3000a2.html",
      "types": ["star", "delta"],
      "images": []
    }
  ]
}
```

Каталог не выбирает одну из них автоматически. Все варианты должны быть доступны интерфейсу и пользователю.

## Схемы соединений

Для каждой связанной страницы `ss*.html` генератор дополнительно пытается определить:

- поддерживается ли соединение `star`;
- поддерживается ли `delta`;
- специальные признаки, например Даландер или переключение полюсов;
- конкретные изображения соединений, если связь между подписью и рисунком определяется однозначно.

Страница соединения и рисунок укладки остаются отдельными сущностями. Они не получают один общий идентификатор.

## Статистика

В корне каждого каталога находится `stats`:

- сколько HTML-страниц просмотрено;
- сколько страниц содержат распознанные варианты укладки;
- сколько отдельных схем найдено;
- сколько уникальных страниц подключения разобрано;
- сколько схем имеют более одной страницы подключения.

Последний показатель особенно важен для проверки требования: возле схемы укладки могут находиться одна или несколько ссылок на схемы подключения, и ни одна из них не должна потеряться.

## Использование в будущем

После проверки качества каталога внешний сайт сможет работать по схеме:

`ESP32 context -> scheme catalog -> список кандидатов -> конкретная укладка + все варианты подключения`.

Это позволит сократить количество динамических чтений старых HTML-файлов и даст стабильную основу для сохранения `scheme_id` в проектах ESP32.

До завершения проверки старый HTML-разбор остаётся резервным и контрольным механизмом.
