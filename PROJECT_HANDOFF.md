## 2. Цель проекта

Переделать дополнительный сайт-справочник для CoilMaster в **один адаптивный сайт для ПК и телефона** вместо двух отдельных копий.

Главные требования пользователя:

- сохранить **все полезные данные сайта**;
- сохранить технические таблицы, схемы, изображения, формулы, пояснения и справочные страницы;
- убрать только доказанные дубликаты, старые служебные файлы и ненужный мусор;
- не держать отдельно расходящиеся desktop/mobile версии;
- сделать современную общую оболочку, пригодную и для ПК, и для мобильных устройств.

## 3. Главное правило сохранности данных

Нельзя удалять технический HTML, изображения, схемы, таблицы или справочные данные только потому, что файл выглядит старым или дублирующимся по имени.

Перед удалением нужно доказать одно из двух:

1. файл байтово/содержательно дублируется в канонической версии; или
2. файл является исключительно служебным метаданным старого FrontPage/редактора и не содержит полезного содержимого сайта.

**Desktop-экспорт выбран каноническим источником**, потому что его главный индекс содержит более полный набор справочных переходов/таблиц, чем mobile-экспорт.

## 4. Что было в исходном репозитории

В `/sourse/` находились две самостоятельные версии справочника:

- desktop;
- mobile.

Они в основном содержали одни и те же технические страницы, изображения и ресурсы. Mobile-версия была отдельной копией, а не независимым набором ценных технических данных.

Во время аудита выполнялось сравнение файлов и Git tree/blob SHA. Было установлено, что основная полезная разница находится в `index.html`: desktop-индекс полнее, а mobile-индекс сокращён. Остальные выявленные различия относились в основном к служебным FrontPage-метаданным.

Контрольные проверки, выполненные ранее:

- legacy `documents/style.css` в desktop и mobile имел одинаковый Git blob SHA;
- контрольная техническая страница `24kss10001500.html` была байтово одинаковой в обеих версиях;
- чистое сравнение desktop → mobile ранее показало всего несколько различающихся файлов (в ходе аудита было зафиксировано 5), при этом значимым содержательным различием был прежде всего индекс.

Если перед финальным удалением какого-либо дополнительного ресурса возникнет сомнение, нужно заново проверить его по текущему Git tree/blob, а не полагаться только на это описание.

## 8. Следующий безопасный блок работ

### Шаг 1 — FrontPage cleanup

Найти в `reference/` каталоги/файлы `_vti_cnf` и другие очевидные FrontPage metadata.

Удалять только те из них, для которых подтверждено, что это служебные метаданные и они не используются сайтом как технический контент.

Не удалять сами HTML-страницы, GIF/JPG/PNG, таблицы, схемы и документы только из-за соседства с `_vti_cnf`.

### Шаг 2 — автоматический structure/link audit

Добавить скрипт/проверку, которая как минимум подтверждает:

- корневая `index.html` существует;
- `assets/` существует;
- `reference/` существует;
- старой `/sourse/` нет;
- ключевые локальные ссылки из новой оболочки ведут на существующие файлы;
- внутренние ссылки канонического справочника не потеряли целевые файлы;
- критические изображения/ресурсы доступны по ожидаемым путям.

Желательно проверять ссылки автоматически, а не вручную по нескольким страницам.

### Шаг 3 — визуальная/адаптивная проверка

Проверить:

- новую главную на широком экране;
- новую главную на узком мобильном экране;
- поиск/навигацию, если они используются;
- несколько характерных страниц из `reference/`;
- длинные таблицы/матрицы, чтобы они не ломали мобильную ширину;
- изображения и схемы, чтобы они масштабировались без потери доступа к данным.

### Шаг 4 — CI и PR

После изменений:

1. проверить актуальный HEAD рабочей ветки;
2. запустить/проверить доступный workflow;
3. не утверждать `SUCCESS`, если GitHub этого фактически не подтвердил;
4. после успешной проверки оформить PR `agent/responsive-reference-site` → `main`.
